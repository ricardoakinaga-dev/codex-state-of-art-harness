# Codex-native gap analysis — frontend engineering

| Boundary | Current/upstream state | vNext requirement |
| --- | --- | --- |
| Identity | Name/description only; no versioned manifest | Exact ID, semver, native manifest, fingerprint and provenance |
| Authority | Builder-oriented examples | Specialist scope, explicit conflicts, no self-approval |
| Architecture | React/Next patterns are presented broadly | Preserve the existing stack; stack selection is evidence-shaped |
| State | useState/useReducer examples | Local/server/URL/derived classification plus loading/success/empty/error/retry |
| Forms | Controlled inputs and basic validation | Native semantics, schema-shaped boundary, server errors, retry and double-submit guard |
| Responsive | General responsive advice | Declared transformations and native captures including intermediate width |
| Accessibility | Illustrative snippets | Keyboard/focus/names/headings/status/contrast/reflow and actual reports |
| Browser evidence | None | Render/source/artifact binding, console/network, interaction receipts |
| Performance | Memoization/code splitting/virtualization examples | Budgeted, measured observations with explicit unavailable states |
| Security | Privacy guidance only in captured fork | Input validation, no external sinks/secrets, security-review handoff |
| Verification | No criterion lineage | Read-only verifier handoff with freshness and final rerun |
| Evaluation | No package-local evals | 50–75 task-shaped positive/negative/false-pass routing scenarios |
| Portability | DOM/React/TypeScript coupling | Existing-stack route and documented framework/dependency boundary |

The native gap is therefore contractual and observational, not merely a need
for more frontend tips. `frontend-engineering-vnext` is intentionally a
specialist and leaves design direction, factual verification, orchestration,
assurance and security approval to their existing owners.
